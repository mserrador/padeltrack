MIGRACION DE GITHUB ACTIONS A RAIZ (PADELTRACK)
================================================

Objetivo
--------
Unificar el despliegue de backend y frontend desde la raiz del repositorio,
eliminar dependencias del modo desarrollo para la demo (npm run dev) y dejar
un flujo de CI/CD reproducible para el nuevo servidor.


1) Estado inicial detectado
---------------------------
- Workflow existente en raiz: .github/workflows/despliegue-backend-vps.yml
- Despliegue previo orientado solo a backend Django.
- Frontend React consumiendo API hardcodeada en localhost.
- docker-compose con un unico servicio (backend).


2) Cambios aplicados en esta migracion
--------------------------------------
2.1 Workflow unificado de GitHub Actions
- Archivo: .github/workflows/despliegue-backend-vps.yml
- Ahora incluye:
  - validacion backend (python manage.py check)
  - build frontend (npm ci + npm run build)
  - despliegue conjunto backend + frontend
- Trigger en push a main para cambios en:
  - backend/**
  - frontend/**
  - requirements.txt
  - docker-compose.yml
  - Caddyfile
  - .dockerignore
  - el propio workflow
- Mantiene workflow_dispatch para ejecucion manual.

2.2 Frontend apto para produccion basica (MVP)
- Archivo: frontend/src/services/api.js
- Se elimina baseURL hardcodeada.
- Nueva baseURL:
  - VITE_API_BASE_URL si existe
  - /api/ por defecto

2.3 Despliegue de frontend estatico
- Archivo nuevo: Caddyfile
- Caddy sirve frontend/dist y hace reverse proxy de /api/* a backend:8000.
- Soporta SPA routing con try_files hacia index.html.

2.4 Docker Compose ampliado
- Archivo: docker-compose.yml
- Se mantiene servicio backend.
- Se agrega servicio caddy:
  - puertos 80 y 443
  - monta frontend/dist como contenido estatico
  - monta Caddyfile
  - usa volumenes caddy_data y caddy_config


3) Flujo final de despliegue
----------------------------
1. Push a main o ejecucion manual del workflow.
2. CI valida backend.
3. CI construye frontend (dist).
4. CI sube por SCP:
   - backend/
   - frontend/dist/
   - requirements.txt
   - docker-compose.yml
   - Caddyfile
   - .dockerignore
5. CI conecta por SSH al VPS y:
   - escribe .env con secrets
   - ejecuta docker compose up -d --build


4) Secrets requeridos en GitHub (Environment: backend-env)
----------------------------------------------------------
Conexion VPS:
- VPS_HOST
- VPS_USER
- VPS_SSH_KEY
- VPS_PORT
- VPS_APP_DIR

Backend Django:
- DJANGO_SECRET_KEY
- DEBUG
- ALLOWED_HOSTS
- CORS_ALLOW_ALL_ORIGINS
- CORS_ALLOWED_ORIGINS
- SQLITE_PATH

Frontend/infra:
- APP_DOMAIN (reservado para evolucion HTTPS por dominio)


5) Preparacion previa del servidor nuevo (obligatoria)
------------------------------------------------------
Checklist minimo antes de lanzar el workflow:

1. Acceder por SSH al servidor.
2. Instalar Docker y plugin docker compose.
3. Crear usuario de despliegue (si no existe) y autorizar clave SSH.
4. Crear carpeta del proyecto, por ejemplo:
   /opt/padeltrack
5. Dar permisos correctos al usuario de despliegue sobre esa carpeta.
6. Abrir firewall:
   - 22/tcp (SSH)
   - 80/tcp (HTTP)
   - 443/tcp (HTTPS)
7. Configurar DNS del dominio (si aplica) apuntando al VPS.


6) Comprobaciones post-despliegue
---------------------------------
Verificar en VPS:
- docker compose ps
- docker compose logs --tail=100 backend
- docker compose logs --tail=100 caddy

Verificar funcionalmente:
- carga de la web en navegador
- login/operaciones basicas contra API
- endpoint API accesible via /api/


7) Riesgos y decisiones para memoria
------------------------------------
Decision clave:
- Para TFG se evita npm run dev en servidor.
- Se usa build estatico del frontend por mayor estabilidad durante la defensa.

Riesgos controlados:
- Dependencia de secrets correctamente definidos.
- Dependencia de apertura de puertos y DNS en el nuevo hosting.
- Persistencia de datos SQLite ligada al volumen/carpeta backend/data.


8) Mejoras futuras recomendadas
-------------------------------
1. Separar workflows: CI (tests/lint) y CD (deploy).
2. Activar HTTPS automatico por dominio en Caddy.
3. Añadir pruebas backend/frontend en CI.
4. Añadir healthcheck de backend y rollback simple.
